# BOBBY'S WORKSHOP
## Universal Software Truth, Integrity & Anti-Fabrication Mandate
### Zero Illusion Engineering Standard (ZIES) — v1.0

**PRIMARY DIRECTIVE**

Build real software that performs real operations, processes authentic data, produces technically defensible results and reports its actual operational state.

Truth, correctness, reproducibility and verifiability take priority over appearance, feature counts, development speed, user satisfaction, positive reporting and release deadlines.

A truthful failure is superior to a fabricated success.

### ARTICLE I — NON-EXHAUSTIVE PROHIBITION
The prohibitions contained in this directive are non-exhaustive. The absence of an explicitly prohibited technique does not constitute permission to use it. Any mechanism, known or unknown, intentional or accidental, that fabricates, substitutes, conceals, distorts, misrepresents, invalidates or artificially influences an operational result must be identified, investigated and corrected.

### ARTICLE II — PRODUCTION AUTHENTICITY
Prohibit fabricated data, mock production responses, placeholder engines, simulated operations presented as real, hardcoded success, fake progress, fake diagnostics, imaginary integrations, artificial telemetry, canned personalized readings, unsupported calculations, invented citations, fabricated confidence scores and misleading capability claims.

### ARTICLE III — COMPUTATIONAL INTEGRITY
Audit every calculation engine, formula, algorithm, transformation, conversion, dependency, lookup table, reference dataset and scoring system. Never substitute unknown values with zero, fabricated defaults or unsupported assumptions. Use independently established reference values and known-answer test vectors wherever available. Distinguish calculated facts from estimates, interpretations, predictions and opinions.

### ARTICLE IV — FAILURE TRANSPARENCY
Prohibit swallowed exceptions, silent failures, concealed errors, undisclosed fallback behavior and success responses that contradict actual operational outcomes. Every failed, incomplete, unsupported, unavailable or unverified operation must expose an appropriate and truthful status. Unknown means unknown. Unverified means unverified. Failed means failed.

### ARTICLE V — END-TO-END VERIFICATION
Trace every advertised user-facing feature through the frontend, backend, service layer, data layer, dependencies, external providers, persistence mechanisms and final observable outcome. A functional interface does not establish functional software. A compiled binary is not proof of correctness.

### ARTICLE VI — TEST AND CI INTEGRITY
Prohibit fabricated tests, empty assertions, circular validation, unjustified test skipping, excessive mocking, suppressed build errors, manipulated benchmarks, misleading coverage statistics and test modifications intended solely to conceal defective functionality. Test actual failures as thoroughly as successful operations.

### ARTICLE VII — AI OUTPUT INTEGRITY
Never permit AI-generated narratives to override verified calculations, source material or observable evidence. Prohibit hallucinated facts, invented research, false citations, artificial personalization, unsupported confidence, fabricated source access and claims of comprehensive review when only partial review occurred.

### ARTICLE VIII — DATA AND STATE INTEGRITY
Audit caching, synchronization, session isolation, database persistence, stale records, duplicate data, race conditions, transactional behavior, corruption handling and cross-user contamination. Never present cached, partial, estimated or historical information as current verified information without appropriate disclosure.

### ARTICLE IX — SECURITY AND DEPENDENCY INTEGRITY
Audit external dependencies, package authenticity, supply-chain risks, hidden network services, permissions, authentication, authorization, integrity checks and production configuration.

### ARTICLE X — RELEASE ARTIFACT INTEGRITY
Verify that the exact distributed binary, package, container, installer or deployed artifact corresponds to the reviewed source revision and intended production configuration. Record source commit identifiers, artifact hashes, dependency versions, build configurations and applicable signing evidence.

### ARTICLE XI — AGENT ACCOUNTABILITY
Distinguish completed work, proposed work, attempted work, failed work and unverified work. Every material accomplishment must be traceable to supporting evidence. Disclose skipped work, incomplete coverage, inaccessible resources, assumptions, limitations and unresolved blockers.

### ARTICLE XII — RECURSIVE REALITY AUDIT
Conduct adversarial inspection of source code, binaries, configuration, tests, CI pipelines, runtime behavior, API responses and documentation. Follow actual execution paths and inspect observable behavior.

### ARTICLE XIII — REQUIRED CLASSIFICATION
Classify every material feature as:
- `REAL — INDEPENDENTLY VERIFIED`
- `REAL — AUTOMATED TESTED`
- `REAL — UNVERIFIED`
- `PARTIAL / BLOCKED`
- `TEST FIXTURE / SIMULATION`
- `INVALID / MISREPRESENTED`
- `NOT IMPLEMENTED`

### ARTICLE XIV — MANDATORY RELEASE GATES
Enforceable CI and release controls (`scripts/zies_gate.py`) prevent known integrity violations from entering production. Unresolved mandatory gate failure blocks release.

### ARTICLE XV — REQUIRED AUDIT DELIVERABLES
Maintain `ZERO_ILLUSION_STANDARD.md`, `REALITY_AUDIT.md`, automated verification tests, and recorded SHA-256 artifact manifests.

### FINAL GOVERNING PRINCIPLE
If a result cannot be established as true, it must not be represented as verified truth. If an operation did not occur, it must not be represented as completed. If a feature has not been verified, it must not be represented as proven functional.
