# Soul Codex — Public Roadmap

This roadmap describes the governed product that Soul Codex is actually willing to ship. Code presence is not the same as production support. The executable system authority is `shared/system-registry.ts`, mirrored in `governance/SYSTEM_REGISTRY.md`.

The product standard is simple: calculate what can be defended, label symbolic interpretation honestly, withhold unsupported certainty, and keep unavailable systems visible as unavailable instead of fabricating completeness.

---

## Live / production-governed foundations

### Profile

Soul Codex builds the strongest profile justified by the supplied evidence.

Current stable identity inputs are:

- verified natal astrology within the governed astronomy contract;
- deterministic numerology core;
- verified Human Design core when the complete trust contract passes.

Exact-time features remain unresolved when exact time, timezone, or location evidence is insufficient. Soul Codex does not silently substitute noon or invent houses, aspects, Nodes, Chiron, Rising, or Human Design values.

The Profile experience also exposes method/status information so users can distinguish calculation evidence from symbolic interpretation.

### Daily

Daily guidance is selective rather than additive.

Current guidance may use:

- deterministic Personal/Universal numerology cycles;
- measured lunar context with optional symbolic reflection;
- verified personal Human Design context where the Human Design trust contract passes.

Daily copy is designed to create distinct reflection questions and concrete experiments without presenting symbolic systems as event prediction, behavioral measurement, luck, or causal energy.

Unsupported legacy systems are not added merely to make a daily reading look larger.

### Compatibility

Compatibility uses the governed evidence-aware relationship path.

- Synastry geometry is calculated from supported chart evidence.
- Relationship language remains symbolic and agency-safe.
- Scores and labels are not presented as empirical predictions of relationship success, destiny, permanence, or compatibility outcomes.
- Malformed or unsupported geometry fails closed rather than receiving a fabricated fallback.

The historical five-pillar stack is not the current production authority.

### Codex Reading

The Codex reading synthesizes qualified evidence into a readable narrative.

- Verified inputs can deepen the reading.
- Repeated themes may be described as symbolic resonance, not extra proof.
- Unsupported systems remain unresolved, inspect-only, or unavailable according to the registry.
- AI-assisted prose may improve clarity, but it may not invent missing evidence or change system qualification status.
- Real-chart differentiation gates actively test for generic or near-duplicate output.

### Systems governance atlas

Soul Codex includes a user-facing systems view that distinguishes:

- **Governed** — production policy exists; per-profile evidence must still qualify.
- **Supporting** — explicit user-assessment context, not stable birth-derived identity.
- **Inspect only** — visible for technical transparency but excluded from verified synthesis.
- **Unavailable** — quarantined until an adequate calculation/evidence contract exists.

## Mobile and release engineering

Native iOS and Android release pipelines are active parts of the product, not out-of-scope ideas.

Current release engineering includes:

- Capacitor-based native packaging;
- iOS/Xcode bootstrap parity checks;
- Android and iOS store-candidate gates;
- exact-head release identity checks;
- production API-routing and native-routing contracts;
- mobile release validation before a candidate is treated as qualified.

A passing build pipeline does not by itself mean a store listing is publicly available. Store publication remains a separate release event.

## Next quality gates

The next product work is focused on depth and trust rather than adding unsupported systems.

1. **Evidence transparency**
   - strengthen concise “why this is included” explanations;
   - preserve privacy while exposing method/status boundaries;
   - keep technical inspection available without overwhelming default views.

2. **Daily usefulness**
   - continue expanding distinct, concrete, non-predictive reflection prompts;
   - reduce repetitive or disclaimer-only copy;
   - preserve system-specific context rather than system pile-on.

3. **Differentiation**
   - continue scaling real-chart and adversarial corpora;
   - reject structural near-duplicates where materially different evidence should change substance;
   - allow legitimate narrative convergence when the evidence actually converges.

4. **Compatibility clarity**
   - improve visual explanation of calculated geometry versus symbolic interpretation;
   - keep relationship agency explicit;
   - maintain fail-closed behavior on incomplete evidence.

5. **Mobile release hardening**
   - preserve exact-head Android/iOS store-candidate qualification;
   - keep Xcode bootstrap parity and native API-routing gates green;
   - treat store publication metadata and binaries as separate release artifacts.

6. **Accessibility and progressive disclosure**
   - maintain reduced-motion support;
   - improve keyboard/screen-reader clarity around evidence and system-status disclosures;
   - keep advanced technical detail available without making it the default reading experience.

## Deferred until the foundation is stronger

These remain intentionally deferred unless a separate governed product decision promotes them:

| Feature | Current reason for deferral |
|---|---|
| Social/community feed | Requires moderation, privacy, abuse-reporting, and social safety contracts beyond symbolic sharing |
| Coach/practitioner marketplace | Requires separate trust, credential, payment, and safety infrastructure |
| Predictive future-forecasting product | Conflicts with the current non-deterministic, reflection-first product doctrine unless redesigned carefully |
| Group compatibility for 3+ people | Adds substantial evidence and UX complexity before two-person compatibility is fully mature |
| Broad third-party health integrations | Not required for the current identity/reflection mission |
| Automatic promotion of legacy mystical systems | Each system must qualify independently; repository code alone is insufficient evidence |

---

## What “ready” means

A Soul Codex feature is ready only when all of the following are true:

1. The calculation path is explicit and testable.
2. Missing or weak evidence fails closed.
3. Privacy boundaries are defined.
4. User-facing language distinguishes calculation from interpretation.
5. Production routes use the governed implementation rather than a legacy compatibility path.
6. Regression tests cover the relevant evidence and wording contracts.
7. Mobile/web release gates remain green on the exact candidate head.
8. Documentation describes the same product the executable registry describes.

That standard is intentionally higher than “the screen renders.”
